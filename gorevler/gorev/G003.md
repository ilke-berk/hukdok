# G003 — HTTP durum kodu disiplini + /process LLM çıktısına Pydantic şeması (sertleştirme 5-B, plan madde 5.3 + 5.4)

- **Bant:** backend
- **Bağımlı:** G001 (şema reddi onun `failed` olayını kullanır)
- **Dosya kapsamı:** `backend/routes/*.py`, `backend/api.py` (handler bağlantıları),
  `backend/analyzer.py` (şema doğrulaması), gerekiyorsa yeni şema modülü
  (`backend/schemas_process.py` gibi), `backend/case_manager.py` (tracking_no 409 tespiti),
  yeni test dosyaları
- **Dokunma:** `backend/config/settings.py` (yeni limit ekleme serbest ama mevcut env adları ve
  varsayılan değerler DEĞİŞMEZ — 5-A bekçi tablosu), G001'in failed mekanizması (KULLAN,
  yeniden icat etme), `docs/guvenilirlik-sertlestirme-uygulama-takibi.md` (G005 senkronlar)

## Hedef
1. **[5.3] Durum kodu disiplini** — 500'e mahkûm edilmiş yanıtlar düzelir:
   - GS/LO timeout ve "sistem meşgul" → 503 (5-A'nın /confirm 503 JSON `detail` biçimiyle
     TUTARLI gövde: kullanıcıya "TEKRAR YÜKLEMEYİN" tarzı yönlendirme nerede uygunsa).
   - Mükerrer config kaydı → 409: `DuplicateItemError` handler'ı `api.py`'de ZATEN var,
     route'lar kullanmıyor — kullandır (`managers/reference_lists.py` fırlatıyor).
   - Not-found → 404, doğrulama hataları → 400.
   - `tracking_no` çakışma tespiti string eşlemeden çıkar: `pgcode == '23505'` + constraint adı.
     DİKKAT: 3-D'nin `/commit` 409 idempotent çözümlemesi ve `[TRACKING_NO_COLLISION]` log
     sözleşmesi (yalnız nihai noktalarda ERROR) BOZULMAMALI — mevcut testler kilitli.
2. **[5.4] /process LLM çıktısına Pydantic şeması** — intake yolu zaten `model_validate_json`
   kullanıyor; /process kullanmıyor → bozuk çıktı varsayılan veriyle "başarılı" dönüyordu.
   Şema reddi artık G001'in terminal olayıyla döner: `{"status":"failed", "error_kod":
   "schema_invalid", "error_ozet": <kullanıcı-dostu mesaj>}`. Kısmİ/gevşek alanlar için şema
   toleranslı olsun (Optional + normalize), amaç bozuk JSON/yapıyı yakalamak — aşırı katı şema
   meşru çıktıyı reddetmesin (yanlış pozitif = kullanıcı kaybı).

## Rapor

### Yapılanlar

**[5.3] Durum kodu disiplini**
- Yeni `backend/db_errors.py`: `is_unique_violation(exc, constraint=None)` /
  `unique_violation_constraint(exc)`. SQLSTATE `23505` (`orig.pgcode`, psycopg3 için
  `orig.sqlstate`) + `orig.diag.constraint_name` okunur; metin eşlemesi yok.
- `managers/case_manager.add_case`: `"tracking_no" in str(getattr(e, "orig", e))` →
  `is_unique_violation(e, TRACKING_NO_UNIQUE_INDEX)`. Sabit `TRACKING_NO_UNIQUE_INDEX =
  "ix_cases_tracking_no"` (canlı DB'de doğrulandı — `unique=True, index=True` UNIQUE INDEX
  üretiyor, `cases_tracking_no_key` DEĞİL). WARNING logu ve `{"error": "duplicate_tracking_no"}`
  dönüşü aynen; 3-D idempotent çözümleme ve `[TRACKING_NO_COLLISION]` sözleşmesi bozulmadı.
- `managers/reference_lists`: `add_item` / `update_item` / `add_email_recipient` artık
  `IntegrityError`'ı ayrı yakalıyor; 23505 ise `DuplicateItemError` yükseltiyor
  (api.py'deki mevcut handler → 409). Ön kontrolü atlatan çakışma eskiden generic
  `except`e düşüp `False` dönüyordu → route'un "Failed to add …" **500**'ü.
- `routes/cases.api_update_case`: `update_case` artık "dava yok" için `None`, hata için
  `False` dönüyor (reference_lists.`update_item` ile aynı ayrım) → **404** / 500.
- `routes/config.api_add_email`: "(maybe duplicate?)" 500 mesajı Türkçeleşti; mükerrer
  vaka artık 409'a gidiyor.
- `api.py`'ye iki 503 ağı: `subprocess.TimeoutExpired` (GS/LO) → 503 +
  `document_pipeline.CONVERSION_BUSY_DETAIL` (5-A ile AYNI metin ve gövde),
  `sqlalchemy.exc.OperationalError` (bağlantı kaybı / havuz tükenmesi /
  `statement_timeout`) → 503 + `DB_BUSY_DETAIL` ("TEKRAR GÖNDERMEYİN").

**[5.4] /process Pydantic şeması**
- Yeni `backend/schemas_process.py`: `ProcessAnalysisOutput` (`extra="allow"`, tüm alanlar
  Optional/varsayılanlı), `validate_process_output()`, `ProcessSchemaError`.
- `analyzer.analyze_file_generator`: `_parse_gemini_json` sonrası `validate_process_output`;
  yeni `except ProcessSchemaError` handler'ı (TEK ERROR) → `_failed_event(..., "schema_invalid")`.
  `_failed_event` docstring'ine (frontend'le ortak dondurulmuş sözleşme) `schema_invalid`
  etiketi eklendi — G001 etiket uzayını kapalı bırakmamıştı.

### Alınan kararlar + gerekçeleri
1. **Kısıt adı ZORUNLU eşleşir.** `cases` tablosunda `uq_cases_sistem_no` da UNIQUE ve
   psycopg2'nin `str(e)` çıktısı `[SQL: INSERT INTO cases (tracking_no, esas_no, …)]`
   ifadesini içeriyor → eski string eşlemesi **her** `cases` IntegrityError'ını (sistem_no
   çakışması, FK ihlali, NOT NULL ihlali) "ofis numarası zaten kayıtlı" sanıyordu ve
   kullanıcıyı boşuna sıra numarası artırmaya itiyordu. Ad bilinmiyorsa (`""`) adlı
   beklentiyle eşleşme YOK sayılır — muhafazakâr taraf.
2. **`managers/reference_lists.py`'ye dokunuldu (kapsam notu).** Görev metni "route'lar
   [DuplicateItemError'ı] kullanmıyor" diyordu; gerçekte route'lar zaten propagate ediyor
   (ön kontrol yolu bugün de 409). Kalan tek 500 yolu `add_item`'in generic `except`inin
   DB-düzeyi 23505'i yutmasıydı — route katmanı yalnız `bool` gördüğü için orada
   düzeltilemezdi. Dosya "Dokunma" listesinde değil; değişiklik üç `except IntegrityError`
   dalıyla sınırlı tutuldu.
3. **`backend/db_errors.py` ayrı modül.** `case_manager` ↔ `reference_lists` arası import
   bağı kurmamak için; kapsamdaki "gerekiyorsa yeni modül" iznine dayanır.
4. **Şema BİLEREK toleranslı.** Sayı→metin, tekil metin→liste, `null` liste→`[]`, boş/None
   öğe elenir, bilinmeyen alanlar korunur. Reddedilen tek şey yapısal karışıklık (kökte
   sözlük olmayan çıktı, skaler yerine sözlük/liste, liste yerine sözlük). Yanlış pozitif =
   meşru analizin çöpe gitmesi; bu takas açıkça yanlış-negatif lehine kuruldu.
5. **Alan haritası korunur.** `validate_process_output` yalnız `raw`'daki anahtarları
   (aynı sırayla) döndürür — şemadaki ama çıktıda olmayan alanları `None`/`[]` olarak
   EKLEMEZ. Aksi halde `sonraki_durusma_tarihi: null` gibi yeni anahtarlar frontend'e
   sızardı; testle kilitli.
6. **`ProcessSchemaError` `ValueError` alt sınıfı DEĞİL.** Generator'ın handler zincirinde
   `json.JSONDecodeError`/`ValueError` yakalayıcıları var; alt sınıf olsaydı şema reddi
   yanlış etiketle (`analysis_error`) raporlanırdı (2026-07-13 `UnicodeDecodeError`
   arızasının aynı deseni). Handler `except ValueError`'dan ÖNCE yerleştirildi.
7. **503 ağları app düzeyinde.** `/confirm`'ün dönüşüm hataları zaten Faz 3-F
   `conversion_pending` katmanına düşüyor ve buraya HİÇ gelmiyor; ağlar o katmanın
   kapsamadığı çağrı yollarının 500 üretmesini engelliyor. `conversion_pending` davranışı
   (belge kaydedilir + gece retry) bilinçli olarak 503'e ÇEVRİLMEDİ — kullanıcı için
   kayıpsız sonuç 503'ten iyidir.
8. **Frontend değişikliği YAPILMADI (kriter gereği).** `frontend/src/lib/api.ts:112`
   `RETRYABLE_GET_STATUSES = {502, 503, 504}` — yalnız GET otomatik tekrarlanır, POST/PUT
   yanıtı çağırana aynen döner. Yeni gövdeler standart `{"detail": str}` biçiminde.
