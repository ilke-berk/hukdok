## Hedef
G195 `cases.status` üzerine `CHECK (status IN CASE_STATUSES) NOT VALID` ekledi. Uygulama yazma yolları buna hazır değil:
- **`add_case`** (`case_manager.py:1512`) status'u normalize ETMEDEN yazar: `status=data.get("status", "DERDEST")`.
  Üçlü dışı değer → `CheckViolation` → `except IntegrityError` dalı (`:1627-1638`) tekil ihlali olmadığı için
  `logger.error` + `None` → `routes/cases.py:77` **500** "Failed to save case".
- **`update_case`** (`:1118-1123`) `normalize_case_status`'tan geçirir ama o fonksiyon tanımadığı metni olduğu gibi
  döndürür ("kapalı liste kapısı çağıranda uygulanır", `constants.py:46-53`) → commit'te `CheckViolation` →
  `except Exception` (`:1239-1242`) ERROR + `False` → `routes/cases.py:307` **500**.
- **`update_case_tracking`** (`:1983-1996`) aynı desen → `except Exception` (`:2015-2018`) ERROR + `False` →
  `routes/cases.py:593` **404** "Dava bulunamadı veya güncelleme başarısız" (yanıltıcı).
- `schemas.CaseCreate.status: str = "DERDEST"` (`schemas.py:308`) serbest metin kabul eder.

Kapı veritabanından ÖNCE: normalize sonrası değer `CASE_STATUSES` dışındaysa istemci hatası yükselir, hiçbir alan
yazılmaz, route **400** döner, ERROR basılmaz (log sözleşmesi: istemci hatası nihai sistem başarısızlığı değil).
Mevcut desen örnek alınır: `stage_decisions.InvalidDecisionStatusError(ValueError)` + `api.py:405-407` handler'ı +
`update_case_tracking`'teki `except InvalidDecisionStatusError: rollback; raise` (`:2010-2014`). `add_case` de
`update_case` gibi `normalize_case_status` kullanır: eski değer (TEMYIZ, KAPALI, …) üçlüye çevrilir, aşama boşsa
`case_stage`'e taşınır (karar 020 — bilgi kaybolmaz). `None`/boş davranışı DEĞİŞMEZ (`add_case` varsayılanı DERDEST;
`update_case` `None`'da dokunmaz; takip yolunda `None` alanı temizler — NULL CHECK'ten geçer, NOT NULL ayrı karar).
