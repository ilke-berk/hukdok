# G092 — Token doğrulama: issuer kontrolü + scp/aud gözlem modu

- **Bant:** backend
- **Bağımlı:** -
- **Dosya kapsamı:** backend/auth_verifier.py, backend/tests/test_auth_verifier.py
- **Dokunma:** backend/dependencies.py (DOKUNMA — kapı sözleşmesi değişmiyor),
  frontend/src/config/msalConfig.ts (DOKUNMA), .env.example (yalnız yeni env
  gerekirse; bu görevde gerekmemeli)

## Hedef

2026-08-22 token analizinin iki bulgusu (O3, O4). `auth_verifier.verify_token`
bugün imzayı, `aud`'u ve `exp`'i doğruluyor ama:

1. **`iss` (issuer) hiç doğrulanmıyor** — `jwt.decode`'a `issuer=` verilmiyor
   (`auth_verifier.py:74-83`). Pratikte `tid` allowlist'i ve imza anahtarının
   **o tid'in** JWKS'inden alınması bunu büyük ölçüde kapatıyor; bu bir açık
   kapatma değil, derinlemesine savunma.
2. **`scp` (scope) hiç okunmuyor** ve `allowed_audiences` çıplak `<client_id>`'yi
   de kabul ediyor (`auth_verifier.py:72`) → aynı uygulama için verilmiş bir
   **ID token**, API access token'ı yerine geçebilir. Yetki yükseltmesi değil
   (aynı kullanıcı), ama "bu token bu API için verildi" garantisi yok.

**2 numaralı kalem bu görevde ZORLANMAZ.** Frontend `api://<client_id>/access_as_user`
scope'u istiyor (`msalConfig.ts:29-31`) ama Azure AD'nin gerçekte hangi `aud`
biçimini ve hangi `scp` değerini bastığı **app registration'daki
`accessTokenAcceptedVersion` ayarına bağlıdır ve repodan doğrulanamaz**. Ölçmeden
sıkılaştırmak herkesi kilitler. Bu yüzden desen G091'in CSP desenidir: **önce
gözlem, sonra ayrı bir görevde zorlama.**

## Yapılacak

### 1. `iss` doğrulaması (zorlayıcı)

İki bilinen biçimin ikisi de kabul edilir — hangisinin geldiği
`accessTokenAcceptedVersion`'a bağlıdır ve repodan bilinemez:

- v2: `https://login.microsoftonline.com/{tid}/v2.0`
- v1: `https://sts.windows.net/{tid}/`

Uygulama: **PyJWT 2.13 `issuer=` parametresine liste/container kabul ediyor**
(konteynerde `jwt.api_jwt.PyJWT._validate_iss` kaynağından doğrulandı,
2026-08-22) — `iss` claim'i hiç yoksa `MissingRequiredClaimError`, listede
yoksa `InvalidIssuerError` fırlar; ikisi de mevcut `except jwt.InvalidTokenError`
dalına düşer. Yani elle kontrole gerek yok. Kritik olan: `tid`'den
türetilen bu iki değerden biri değilse **token reddedilir**, mevcut ret
yollarıyla aynı biçimde (None döner, WARNING/ERROR loglanır).

### 2. `scp` + `aud` gözlemi (davranışsız)

Token kabul edilmeye devam eder, yalnız **süreç başına BİR KEZ** WARNING
loglanır:

- `scp` claim'i yoksa ya da içinde `access_as_user` yoksa
- `aud` çıplak `<client_id>` (yani `api://` önekli değil)

`verify_token` **her istekte** koşuyor — istek başına log basılırsa log seli
olur ve log sözleşmesi bozulur. Tek-seferlik bayrak deseni repoda zaten var:
`routes/export.py:52-62` (`_weak_key_warned`). Log satırı ölçüm için yeterince
bilgi taşımalı: gözlenen `aud` biçimi ve `scp` değeri (token'ın KENDİSİ ASLA
loglanmaz).

## Bu görevin KAPSAMADIĞI doğrulama (kullanıcıya kalır)

Testler **uydurma** token'larla koşuyor (gerçek RSA imzası var ama claim'ler
sentetik). `iss` zorlaması gerçek Azure AD token'ına karşı **hiç
denenmemiş** olur. Deploy'dan önce insan adımı:

```
docker compose build backend && docker compose up -d backend
```

sonra tarayıcıda `http://localhost:8080` → gerçek Microsoft girişi → dava
listesi açılıyor mu. **401 alınıyorsa `iss` biçimi tahminimizden farklı
demektir** — backend logundan gerçek `iss` okunup görev yeniden açılır.

Aynı turdan sonra `docker compose logs backend | grep -i "scp\|audience"`
çalıştırılıp gözlem WARNING'leri toplanır: **faz 2 (scp zorunluluğu + audience
daraltma) bu çıktıya bakan AYRI bir görevdir**, bu görevde YAPILMAZ.
