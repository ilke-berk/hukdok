# G041 — D 6.1: eksik kısıt/index'leri çalışan op türüne taşı

- **Bant:** backend
- **Bağımlı:** -
- **Dosya kapsamı:** backend/database.py, backend/tests/test_migration_path.py
- **Dokunma:** backend/models.py (DOKUNMA — G044/G045'in bandı), diğer testler

## Hedef

`create_all()` (`database.py:107`) tabloları modelden **önce** yaratıyor; migrasyon tablo
listesini **sonra** okuyor (`:540`) → `("table", …)` op'ları `if table in tables: continue`
ile atlanıyor (`:587-588`). Sonuç: o op'ların taşıdığı UNIQUE kısıt ve index SQL'leri
**hiç çalışmamış**. `models.py`'de `__table_args__`/`UniqueConstraint`/`Index(` → **0 eşleşme**,
yani ORM da bunları ifade etmiyor.

Çözüm ucuz: `("index", tablo, [...])` op türü **zaten çalışıyor** (canlı kanıt:
`uq_cases_sistem_no`, `idx_case_docs_conversion_pending` prod'da VAR). Eksik kalemler
bu mevcut op türüne taşınır. Yeni mekanizma ya da Alembic GEREKMİYOR.

## Kabul kriterleri

- [ ] Sekiz kalem `("index", tablo, [...])` op'una taşındı; hepsi `IF NOT EXISTS` ile
      idempotent. UNIQUE'ler `CREATE UNIQUE INDEX IF NOT EXISTS` biçiminde
      (`ALTER TABLE ADD CONSTRAINT` idempotent DEĞİL — tekrar koşuda patlar)
- [ ] `("table", …)` op'larının gövdesindeki artık kısıt/index SQL'leri **kaldırılmadı**
      (yeni bir kurulumda tablo sıfırdan yaratılırken hâlâ gerekli) — ama yeni `index`
      op'larıyla **çakışmadıkları** doğrulandı (`IF NOT EXISTS` ikisini de güvenli kılar)
- [ ] **Savunmacı UNIQUE:** migrasyon UNIQUE index yaratmadan önce mükerrer kontrolü
      yapıyor; mükerrer varsa **anlaşılır bir hata** ile duruyor (fail-fast doğru davranış —
      ama "duplicate key value violates unique constraint" yerine hangi tablo/kolon/kaç grup
      olduğunu söyleyen bir mesaj). Konteyner kalkmaması BİLİNÇLİ, sessiz atlama YASAK
- [ ] `test_migration_path.py`'deki iki "bugünkü kusuru kilitleyen" test **ters çevrildi**:
      `test_table_op_index_sqlleri_bugun_hic_calismiyor` artık index'lerin **oluştuğunu**
      iddia ediyor (ad da güncellendi). G031 bu devri açıkça öngörmüştü
- [ ] `test_columns_op_post_index_sqlleri_bugun_hic_calismiyor` için karar verildi ve
      gerekçesi rapora yazıldı: ölçüldü ki `columns` post_sql'leri **çoğunlukla koşmuş**
      (kolon gerçekten sonradan eklendiğinde çalışıyor); bu testin ne iddia ettiği
      gözden geçirilmeli — yanıltıcıysa daraltılmalı
- [ ] Boş DB'ye sıfırdan kurulum + ikinci koşu (idempotency) hâlâ yeşil
- [ ] `docs/mimari/` içinde migrasyon mekanizmasını anlatan yer güncellendi
